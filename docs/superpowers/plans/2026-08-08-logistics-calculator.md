# Расчёт доставки перевозчиками — план реализации

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Заказчик, открыв КП, видит не только цену изготовления, но и во что обойдётся привезти изделие к себе — с выбором из нескольких перевозчиков, а не одним числом от платформы.

**Architecture:** Каждый перевозчик — модуль в `lib/logistics/` с общим контрактом `quote(params) → Quote | null`. Реестр `lib/logistics/index.js` опрашивает всех параллельно и переживает молчание любого. Города разрешаются через `lib/logistics/geo.js`: канонический справочник в БД плюс код каждого перевозчика, добываемый его же справочником и кэшируемый.

**Tech Stack:** CommonJS, PostgreSQL через `pool`, схема правится `ALTER TABLE ... IF NOT EXISTS` (как везде в `db.js`), тесты — `node:test` через `scripts/run-unit-tests.js`, фронт — ванильный JS без сборки.

**Спека:** `docs/superpowers/specs/2026-08-08-logistics-calculator-design.md`

## Global Constraints

- **Ни один внешний перевозчик не попадает в деплойный гейт.** `npm test` не должен ходить в сеть: юниты гоняются на сохранённых ответах в `tests/fixtures/logistics/`. Живая проверка — отдельный `npm run check:logistics`.
- **Молчащий перевозчик выпадает из выдачи, а не роняет ответ.** Таймаут 8 секунд, `Promise.allSettled`.
- Никаких новых зависимостей: HTTP через встроенный `fetch` (Node 18+), как в остальных интеграциях.
- Все цены в интерфейсе — с оговоркой про публичный тариф. Голого числа без неё не существует.
- Свободный текст города в расчёт не передаётся никогда. Только разрешённая точка из справочника.
- Комментарии и тексты — по-русски, тон как в проекте: объясняем последствие, а не описываем поле.

### Task 1: Гео-слой

**Files:**
- Create: `lib/logistics/geo.js`, `scripts/sync-logistics-cities.js`
- Modify: `db.js` (таблица `logistics_cities`)

**Interfaces:**
- Produces: `resolveCity(pool, query)` → `{ status: 'ok' | 'not_found' | 'ambiguous', point, candidates }`; `suggestCities(pool, query, limit)` → массив для подсказок в форме; `pickCity(rows)` — чистый выбор среди совпавших.

- [x] **Step 1: Таблица**

```sql
CREATE TABLE IF NOT EXISTS logistics_cities (
    id          SERIAL      PRIMARY KEY,
    name        TEXT        NOT NULL,
    qualifier   TEXT        NOT NULL DEFAULT '',  -- «Алтайский р-н» из скобок
    search_key  TEXT        NOT NULL,             -- нормализованное имя, НЕ уникально
    pecom_id    TEXT        UNIQUE,
    pecom_hub   TEXT        NOT NULL DEFAULT '',
    dellin_code TEXT,                             -- КЛАДР, добывается лениво
    is_hub      BOOLEAN     NOT NULL DEFAULT false,
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
CREATE INDEX IF NOT EXISTS logistics_cities_key ON logistics_cities (search_key);
```

- [x] **Step 2: Загрузка справочника ПЭК**

`scripts/sync-logistics-cities.js` тянет `https://pecom.ru/ru/calc/towns.php` (≈586 КБ JSON, без ключа) и раскладывает в таблицу пачками по 500.

Формат ответа — объект, где ключ это город-хаб, а значение объект `{ "<id>": "<название города>" }`. Отрицательные id — сами хабы, положительные — населённые пункты в их зоне. **Замерено 2026-08-08:** 225 хабов, 4810 записей, ровно один отрицательный id на группу.

Нормализация `search_key`: нижний регистр, `ё → е`, срезаются `г.`, `пос.`, `с.`, скобочные уточнения района, дефис приравнен к пробелу. Плюс словарь разговорных форм — «СПб», «питер», «ЕКБ»: в `companies.city` лежит именно это.

- [x] **Step 3: Разрешение города — без угадывания**

Первоначальный замысел («при неоднозначности берём хаб») разбился о данные: **307 названий в справочнике встречаются больше одного раза, и хаб помогает лишь в 18 случаях.** «Белый Яр» есть под Абаканом и под Сургутом — 2500 км между ними. Уникальный `search_key` означал бы молчаливый выбор одного из двух и цену доставки до чужого города, которой человек поверит.

Поэтому `resolveCity` возвращает не город, а исход: `ok` / `not_found` / `ambiguous` со списком кандидатов и уточнением района у каждого. Выбирает человек. Логика выбора вынесена в чистую `pickCity(rows)` и проверяется без базы.

`dellin_code` на этом этапе пустой — заполняется в Task 6, когда появится ключ. Отсутствие кода означает «этот перевозчик по этому маршруту не считает», а не ошибку.

- [x] **Step 4: Тест**

`tests/unit/logistics-geo.test.js`: нормализация имён, разбор справочника, все три исхода `pickCity`, пачечная запись. 20 тестов, зелёные; полный прогон — 290 passed.

### Task 2: Модуль ПЭК

**Files:**
- Create: `lib/logistics/pecom.js`, `tests/fixtures/logistics/pecom-msk-ekb.json`

**Interfaces:**
- Produces: `quote({ from, to, places, insurance, doorFrom, doorTo })` → массив `Quote` (авто и авиа — разные варианты).

- [x] **Step 1: Запрос**

GET на `https://calc.pecom.ru/bitrix/components/pecom/calc/ajax.php`. Места передаются повторяющимися параметрами в жёстком порядке: `places[N][]` = ширина, длина, высота, объём, вес, негабарит (0/1), жёсткая упаковка (0/1). Метры и килограммы.

Проверенный запрос (Москва → Екатеринбург, 1 м³, 500 кг, страховка 100 000 ₽) даёт `auto: 12900`, `take: 2650`, `deliver: 1350`, `ADD_3` (страхование) `681.6`, срок «4 - 7».

- [x] **Step 2: Разбор ответа**

Цены лежат массивами `["Стоимость перевозки груза", "Москва Восток - Екатеринбург", 12900]` — берём последний элемент. Услуги в `ADD_1`…`ADD_N` объектами `{1: название, 3: сумма}`, **номер за услугой не закреплён** — ищем по названию, а не по индексу.

Про сроки в плане было сказано, что они приходят только HTML-строкой. На деле у наземной доставки есть структурное поле `periods_days` («4 - 7») — регулярка по разметке нужна лишь для авиа (`aperiods`) и как запасной вариант. Не разобралось — `days: null`, а не выдуманное число: в таблице лучше прочерк.

Округление: каждая составляющая округляется отдельно, итог считается их суммой. Иначе разбивка на экране не сходится с итогом — страхование приходит как `681.6`.

Комментарием в файле зафиксировано, что эндпоинт — ajax-компонент их сайта на Битриксе, без гарантий обратной совместимости, и что именно поэтому есть `check:logistics`.

- [x] **Step 3: Фикстура и тест**

Живой ответ сохранён в `tests/fixtures/logistics/pecom-msk-ekb.json`. `tests/unit/logistics-pecom.test.js` — 21 тест на фикстуре, **без сети**. Отдельно проверено вживую: `quote()` по маршруту Москва → Екатеринбург даёт авто 17 582 ₽ (4–7 сут.) и авиа 96 182 ₽ (1–5 сут.).

### Task 3: Реестр, кэш, деградация

**Files:**
- Create: `lib/logistics/index.js`
- Modify: `db.js` (таблица `logistics_quotes_cache`)

**Interfaces:**
- Produces: `quoteAll(pool, params)` → `{ quotes: Quote[], failed: string[], cachedAt }`.

- [x] **Step 1: Параллельный опрос**

`Promise.allSettled` по всем зарегистрированным перевозчикам, сторожевой таймер 8 секунд поверх каждого — свой таймаут на `fetch` у модулей есть, но зависнуть можно и на разборе ответа. Упавшие и отвалившиеся по таймауту попадают в `failed`.

Пустой ответ отказом не считается: «этот перевозчик сюда не возит» — такой же результат, и в `failed` ему не место.

Сортировка результата по итоговой цене.

- [x] **Step 2: Кэш**

Ключ считается **от точного запроса**, а не от округлённых веса и объёма, как задумывалось. Округление меняет тарифную ступень, то есть человек увидел бы цену за другой груз; выигрыш при этом небольшой — повторы в жизни и так точные, одну и ту же карточку КП открывают много раз. Ключ — sha1 нормализованного запроса, TTL 24 часа.

Пустой ответ кэшируется наравне с обычным: переспрашивать «не возит ли теперь» каждый показ незачем.

Сбой записи в кэш расчёт не ломает: кэш — ускорение, а не источник правды.

- [x] **Step 3: Тест**

`tests/unit/logistics-registry.test.js` — 10 тестов на подставных перевозчиках: падение, зависание дольше таймаута, молчание всех разом, пустой ответ, сортировка, попадание в кэш, испорченная запись в кэше, недоступная база.

- [x] **Step 4: Коммит**

```bash
git add lib/logistics/index.js db.js tests/unit/logistics-registry.test.js
git commit -m "feat(logistics): реестр перевозчиков, кэш и деградация при отказе"
```

### Task 4: Габариты в КП

**Files:**
- Modify: `db.js` (колонки в `proposals`), `routes/proposals.js` (`POST /`, ~строка 92), `producer.html` (форма подачи КП)

**Решение владельца:** габариты спрашиваем у завода при подаче КП, а не у заказчика в форме заявки. Завод знает вес готового изделия точно, заказчик обычно нет; плюс форма заявки не растёт — за её конверсию боролись в онбординге.

- [x] **Step 1: Колонки**

```sql
ALTER TABLE proposals ADD COLUMN IF NOT EXISTS cargo_weight  REAL;
ALTER TABLE proposals ADD COLUMN IF NOT EXISTS cargo_length  REAL;
ALTER TABLE proposals ADD COLUMN IF NOT EXISTS cargo_width   REAL;
ALTER TABLE proposals ADD COLUMN IF NOT EXISTS cargo_height  REAL;
ALTER TABLE proposals ADD COLUMN IF NOT EXISTS cargo_places  INTEGER;
```

Все поля необязательные. КП без габаритов остаётся валидным — иначе сломаем подачу КП ради вспомогательной фичи.

- [x] **Step 2: Приём в API**

Разбор вынесен в `lib/logistics/cargo.js` — чистый модуль, тестируется без HTTP. Положительные числа, вес до 20 000 кг, размер до 20 м, запятая как разделитель («1,25» у нас пишут чаще точки). Мусор молча не сохраняется, а не роняет подачу КП.

Поля добавлены и в `POST /`, и в `PUT /:proposalId`. В `PUT` габариты трогаются только если форма их прислала: старые клиенты этих полей не знают, и молчание не должно стирать уже указанное.

`rowToProposal` в `server.js` отдаёт `cargo` наружу — иначе расчёт их не увидит.

- [x] **Step 3: Форма**

В `producer.html`, в форме КП — свёрнутый `<details>` «Габариты для расчёта доставки»: вес одного места, количество мест, длина, ширина, высота. Подсказка в стиле `.form-hint`:

> Заказчик увидит стоимость доставки от нескольких перевозчиков и полную сумму сделки. Без габаритов расчёта не будет.

Вес спрашивается **за место**, а не за партию: иначе при «2 места по 300 кг» пришлось бы гадать, 300 это каждое или всё вместе.

- [x] **Step 4: Проверить глазами на 390px**

Поднят локальный PostgreSQL и тестовые данные, снято в Chromium на 390 и 1440: сетка полей в две колонки, подписи читаются, горизонтального вылета нет, JS-ошибок нет.

- [x] **Step 5: Тест**

`tests/unit/proposal-cargo.test.js` — 13 тестов: разбор значений, запятая, невозможные величины, разворот в места для перевозчика, плюс три через реальный роутер — КП с габаритами, без габаритов и с мусором в полях.

- [ ] **Step 6: Коммит**


### Task 5: API расчёта и витрина в КП

**Files:**
- Create: `routes/logistics.js`
- Modify: `server.js` (подключение роутера), `index.html` (блок в карточке КП), `assets/app.js` (рендер)

**Interfaces:**
- Produces: `GET /api/logistics/quote?proposalId=N` и `GET /api/logistics/cities?q=`.

- [x] **Step 1: Роут**

`proposalId` → габариты из КП, город завода и город заказчика из `companies.city` через `resolveCity`. Осмысленные ошибки вместо пустоты, каждая со своим `reason`: `no_cargo`, `from_city`, `to_city`. Город-двойник не выбирается молча — просим уточнить профиль.

Страхуем на цену предложения. Общий `generalLimiter` (60 запросов в минуту на `/api/`) уже покрывает роут, отдельный не заводим.

`quoteAll` инжектируется через deps: иначе юниты пошли бы в сеть к перевозчикам, а гейт не должен зависеть от чужих сайтов. Тест на маршрут упал с 2,4 с до 3,7 мс.

- [x] **Step 2: Витрина**

Блок раскрывается в строке КП по кнопке «Рассчитать доставку». Кнопка показывается только там, где расчёт возможен: без габаритов от завода предлагать действие, которое упрётся в отказ, незачем.

Загрузка ленивая и однократная — чужой API не дёргается на каждую отрисовку списка.

Оговорка под расчётом обязательна, без неё цену де-факто обещает платформа:

> Ориентировочный расчёт по публичному тарифу перевозчика. Не учитывает обрешётку, негабарит и класс груза. Итоговую стоимость подтверждает перевозчик.

- [x] **Step 3: Проверить на 390px**

Первая версия была таблицей на пять колонок — на снимке с 390px оказалось, что видна только колонка с названиями перевозчиков, а цена и срок ушли за экран. То есть человек не видел ровно того, ради чего открывал блок.

Переделано в строки на флексе: перевозчик и способ слева, цена и «Оформить» справа, разбивка под ними. Горизонтальной прокрутки нет ни на 390, ни на 1440.

Отдельно замерено: таблица откликов и до раскрытия расчёта шире модалки (775px против 654px), то есть обрезанная колонка действий — давняя особенность, а не регрессия этой правки.

- [x] **Step 4: Тесты и коммит**

`tests/unit/logistics-route.test.js` — 10 тестов: все три причины отказа, чужое КП, сборка мест по количеству, молчание перевозчиков.

## Порядок

Задачи 1–3 дают работающий расчёт, но без интерфейса. Задачи 4–5 доводят до пользы. **Точка решения — после Task 6:** пока перевозчик один, сравнивать не с чем, и судить по этому, работает идея или нет, нельзя. Task 7 можно делать в любой момент после Task 2.

Публичная страница-калькулятор под SEO — отдельным планом после того, как внутренний сценарий обкатан. Она единственная из всего списка бьёт в спрос, который в роадмапе назван главным ограничением, но делать её раньше внутренней витрины смысла нет: нечего будет показывать.
